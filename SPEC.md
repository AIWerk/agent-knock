# Agent Knock - Specification v0.3 (draft)

2026-11-14 · Attila Bergsmann, AIWerk (aiwerk.ch)

Status: draft for public comment. License: CC BY 4.0.

## Changes since v0.2

v0.3 builds on a rethink from 2026-11-14: if the caller finds the callee's A2A endpoint before the call, it does not phone but connects directly. The handshake is therefore meant for the case where the caller knows only the phone number. Three changes follow from this.

- **The callee signals first (ANNOUNCE).** When answering the call, the callee sends a short frame and only then greets. The caller sends HELLO only in response to this signal. A human, an interactive voice menu or an agent that does not know the protocol therefore never receives a HELLO (section 4).
- **The domain comes from the call (default case).** The callee always sends its domain in the OFFER. The v0.2 default case without a domain has been removed, because it assumed a known domain, and with a known domain the caller would not phone (section 8).
- **The domain can span several frames (DOMAIN continuation).** The OFFER holds 15 characters, a continuation frame another 22. With at most two continuation frames, a domain of up to 59 characters can be transmitted (sections 6-7).
- The AI announcement made in speech is no longer the trigger of the handshake but a transparency rule: whoever speaks with a human states that it is an AI (section 14).
- The upper limit for the complete handshake is 60 seconds instead of 45, because of the longer domain.
- Version code: `03`.
- 2026-11-15: the listening window after the ANNOUNCE was shortened from 2 seconds to 0.5 seconds, so that a human caller hears no noticeable silence. A slower caller still gets in by interrupting the greeting (section 4).

## 1. Purpose and scope

This specification describes how two AI agents switch from an ongoing phone call to a fast, verified internet data channel. The call serves only for recognition and code exchange; the actual business is conducted over the A2A protocol.

Name: **Agent Knock**. The Hungarian working title was TAK (telefonos ágens-kézfogás, "phone agent handshake"); the abbreviation is already taken in English (Team Awareness Kit), so the English name is used publicly. Status: third draft. Part of the transmission has been measured on a real line; the complete handshake is not yet implemented.

**When the handshake is needed.** If the caller finds the callee's A2A endpoint before the call (from its own data, from the company website, from a number registry), it SHOULD connect directly over A2A, without a phone call. The handshake is meant for the case where the caller knows only the phone number, or does not even know that there will be an agent on the other end. In that case the call itself is the discovery: the callee says in the call where it can be reached.

What it defines:

- recognition and initiation of the handshake within the call,
- the format and transmission of messages sent as DTMF signals,
- transmission of the callee's domain,
- the mutual verification that binds the call to the data channel,
- the fallback to human speech if anything fails.

What it does not define:

- the lookup before the call (number registry, agent card lookup); this is the subject of a separate supplement,
- the content and data fields of the business (appointment, order, quote),
- what the agent is authorised to do on behalf of its principal,
- proof of the caller's identity.

Design principles:

- It builds only on existing infrastructure: the telephone network, DTMF (RFC 4733), HTTPS, the callee's own domain, A2A.
- It requires no directory or registry.
- If the other party does not know it, the call continues with speech exactly as it would without it.

In this text the words MUST, MUST NOT, SHOULD and MAY denote mandatory, prohibited, recommended and permitted behaviour respectively.

## 2. Terms and roles

| Term | Meaning |
|---|---|
| Caller | The agent that initiates the call. On the data channel it is the client. |
| Callee | The agent that receives the call. It operates the endpoint. |
| Handshake | The DTMF message exchange taking place within the call (sections 4-6). |
| Frame | One DTMF message, from the opening `*` to the closing `#`. |
| Announcement (ANNOUNCE) | The callee's first frame, by which it signals that it knows the protocol. |
| Caller code (A) | A 6-digit random number generated by the caller. |
| Callee code (B) | A 6-digit random number generated by the callee. |
| Session identifier (S) | A 4-digit number issued by the callee that identifies the call at the endpoint. Not secret. |
| Agent card | The machine-readable business card according to A2A, on the callee's domain. |
| Handoff endpoint | The callee's HTTPS address where the mutual verification takes place (section 9). |
| Known domain | The callee's domain, if the caller already knows it before the call from the same source as the phone number. |
| Frame handler | The deterministic component that produces and verifies the frames (section 11). |

## 3. Overview

The process consists of three phases: handshake in the call, verification over the internet, business over A2A.

**In the call**

1. The caller dials the number.
2. On answering the call, the callee sends an ANNOUNCE frame and waits briefly.
3. If the caller knows the protocol, it responds with a HELLO frame containing the caller code (A). If it does not know it, or is a human, it simply starts speaking, and the callee greets.
4. The callee responds with an OFFER frame: session identifier (S), callee code (B) and the beginning of the domain. If the domain is longer than 15 characters, one or two DOMAIN continuation frames follow.
5. The caller acknowledges with an ACK frame.

**Over the internet**

6. The caller fetches the agent card from the received domain and reads the address of the handoff endpoint from it.
7. The caller sends the S identifier to the endpoint.
8. The endpoint sends back the A code. This proves that it is the same party that answered the phone.
9. The caller sends the B code. This proves that it was in the call.
10. The endpoint issues a short-lived access token.

**The business**

11. The caller sends standard A2A messages with the token; the call can be hung up.

If no HELLO arrives in step 3, the callee greets and the call continues with speech. If any later step fails, both parties continue with speech in the same call.

## 4. Recognition and initiation

The handshake is always made possible by the callee's ANNOUNCE frame and started by the caller's HELLO frame. There is at most one handshake per call.

**On the callee side**

- On answering the call, before saying anything, the callee MUST send an ANNOUNCE frame. If the call is first taken by a menu system or a human and only later reaches the agent, the ANNOUNCE is sent when the agent takes over the call.
- After the ANNOUNCE, the callee waits silently for at most 0.5 seconds (listening window). It starts the greeting when the window expires or when the caller starts speaking, whichever happens first.
- If a `*` arrives within the window, the callee stays silent and waits for the HELLO frame.
- If the HELLO arrives during the greeting, the callee SHOULD stop speaking and continue with the handshake. It MUST accept the HELLO for 10 seconds from the end of the ANNOUNCE; after that it may ignore it.
- At most one ANNOUNCE may be sent per call.

**On the caller side**

- The caller may send HELLO only after a valid ANNOUNCE. Without an ANNOUNCE it MUST NOT send HELLO, even if the other end appears to be a machine.
- The caller SHOULD send the HELLO as soon as possible after the ANNOUNCE. A caller running on a language model will usually miss the short listening window; its HELLO then arrives during the greeting, which the callee interrupts. This is the expected case, not an error.
- If the version in the ANNOUNCE is unknown to it, the caller does not send HELLO and continues with speech.
- During the handshake neither agent speaks.
- If no OFFER frame starts within 6 seconds after the end of the HELLO, the caller continues with speech. There is no retry.

**Human caller.** Whether a human caller hears the ANNOUNCE depends on the network path. Where a gateway converts RFC 4733 events into audio, it is a tone of about 1 second after pickup. In the real-line test from a Swiss mobile phone no tone was audible at all (section 13). After it comes at most half a second of silence, or the greeting right away if they speak.

## 5. DTMF frame and transmission

Every message is one frame: opening `*`, two-digit type, data fields, two check digits, closing `#`.

```
*  TT  data...  CC  #
```

**Signal set.** Only the 12 common signals may be used: `0`-`9`, `*`, `#`. The signals A-D MUST NOT be used, because not every network transmits them. `*` and `#` mark exclusively the start and end of a frame.

**Transmission.**

- In a SIP call the signals MUST be sent as out-of-band events (RFC 4733, telephone-event).
- In-band sending MAY be used only if the sending platform cannot do RFC 4733. The receiver cannot rely on recognising a frame that arrives in-band: on mobile networks and speech-processing platforms these do not get through (section 13).

**Timing.**

- Default rate: 100 ms signal, 100 ms pause, i.e. 5 signals per second.
- Permitted faster rate: at least 70 ms signal and 70 ms pause, i.e. about 7 signals per second.
- The receiver MUST accept a 70 ms signal. In the measurements the network shortened signals to 70 ms (test 1) and to about 57-61 ms (test 2), regardless of the length sent; Asterisk pads signals shorter than 80 ms.
- At most 1 second may elapse between two signals, otherwise the receiver discards the incomplete frame.
- Between consecutive frames (for example OFFER and DOMAIN continuation) the sender MUST keep a pause of at least 300 ms, so that the receiving platform treats the frame as closed.

**Frame length.** A frame may be at most 50 signals, not counting the closing `#`. Some receiving platforms cannot take a longer one in a single piece (the ElevenLabs buffer is 50 signals). This is why a longer domain is sent in several frames (section 7).

**Check digits (CC).** The ISO 7064 MOD 97-10 method, the same one used by IBAN:

1. Take the digits of the type and the data fields as a single number (N).
2. CC = 98 - (N × 100 mod 97), padded to two digits.
3. The receiver takes the complete digit sequence (type, data, CC) as one number. The frame is valid if this leaves a remainder of 1 when divided by 97.

**Length check.** The receiver MUST also check the frame length based on the type (section 6). A dropped or duplicated signal is thus detected even if the check digits happen to match.

Type codes never begin with zero, so N has no leading zero.

## 6. Handshake messages

There are seven frame types. The fields follow each other in the given order, without separators.

| Type | Name | Direction | Fields (digits) | Total digits, including CC |
|---|---|---|---|---|
| 14 | ANNOUNCE | callee → caller | highest supported version (2) | 6 |
| 10 | HELLO | caller → callee | version (2), A code (6) | 12 |
| 11 | OFFER | callee → caller | version (2), S (4), B code (6), domain length L (2), the first at most 15 characters of the domain (2 per character) | 18 + 2 × min(L, 15) |
| 13 | DOMAIN | callee → caller | sequence number (1), the next at most 22 characters of the domain | 5 + 2 × number of characters |
| 12 | ACK | caller → callee | none | 4 |
| 19 | NAK | either | none | 4 |
| 99 | ABORT | either | none | 4 |

**Rules**

- Version: the code of this draft is `03`. The ANNOUNCE states the highest version supported by the callee. The HELLO version may not be higher than that, and the OFFER version may not be higher than the HELLO version. On an unknown version: ABORT.
- A and B codes: MUST be generated with a cryptographically secure random number generator. They are single-use and valid for 120 seconds from the sending of the OFFER.
- S: MUST be unique among the callee's active sessions.
- Domain length (L): the number of characters of the complete domain, between 1 and 59. If L is at most 15, the complete domain is in the OFFER. If it is greater, the remainder comes in DOMAIN frames: the one with sequence number 1 carries characters 16-37, the one with sequence number 2 carries characters 38-59. The caller knows from L how many DOMAIN frames to expect.
- The DOMAIN frames come directly after the OFFER, in order of sequence number, with the pause between them (section 5).
- ACK: the caller sends it after error-free reception of the OFFER and all expected DOMAIN frames. From then on the caller continues over the internet.
- NAK: after an invalid or missing frame. In the OFFER group (OFFER and DOMAIN frames) a NAK requests retransmission of the whole group. It may be sent at most twice per group or per frame respectively.
- ABORT: end of the handshake. Both parties continue with speech.

**Example frames**

| Frame | Example | Signals |
|---|---|---|
| ANNOUNCE (version 03) | `*140360#` | 8 |
| HELLO (A = 739104) | `*100373910455#` | 14 |
| OFFER `aiwerk.ch` (S = 4821, B = 520466, L = 9) | `*110348215204660901092305181141030863#` | 38 |
| OFFER `fogaszat-muster.ch`, first 15 characters (L = 18) | `*110348215204661806150701192601204013211920051841#` | 50 |
| DOMAIN 1, `.ch` | `*13141030866#` | 13 |
| ACK | `*1262#` | 6 |
| NAK | `*1941#` | 6 |
| ABORT | `*9992#` | 6 |

**Time required**

| Case | Total signals | 5 signals/s | 7 signals/s |
|---|---|---|---|
| `aiwerk.ch` (9 characters, one OFFER) | 66 | 13.2 s | 9.4 s |
| `fogaszat-muster.ch` (18 characters, OFFER + 1 DOMAIN) | 91 | 18.2 s | 13.0 s |
| 37-character domain (OFFER + 1 DOMAIN) | 129 | 25.8 s | 18.4 s |

To this add the reaction time of both parties, 1-3 seconds per frame on a platform running on a language model. A shorter domain gives a faster handshake; the callee SHOULD use the shortest possible domain or subdomain under which its card is reachable. The signal time is a calculated value; signal transmission has been partly measured (section 13), the complete handshake not yet.

## 7. Domain encoding

Every character of the domain becomes two digits according to the table below.

| Character | Code |
|---|---|
| a-z | 01-26 (a = 01, b = 02, ... z = 26) |
| 0-9 | 30-39 (0 = 30, 1 = 31, ... 9 = 39) |
| hyphen (-) | 40 |
| dot (.) | 41 |

- Only the host name is transmitted: no `https://`, port or path.
- Only lower case may be used. An internationalised domain name is transmitted in its standard ASCII form (`xn--...`).
- At most 59 characters (OFFER 15 + two DOMAIN frames of 22 each).
- All other codes are reserved. If the receiver gets one, the frame is invalid.

Example: `fogaszat-muster.ch` (18 characters)

```
f  o  g  a  s  z  a  t  -  m  u  s  t  e  r   |  .  c  h
06 15 07 01 19 26 01 20 40 13 21 19 20 05 18   |  41 03 08
            OFFER (first 15 characters)         |  DOMAIN 1
```

## 8. The domain and the endpoint

### 8.1 Source of the domain

- **Default case: the domain comes from the call.** The caller uses the domain received in the OFFER and DOMAIN frames.
- **If the caller knows the domain** (from the same source as the phone number) and the one received in the call differs from it, it MUST NOT use the one received in the call. It sends ABORT and continues with speech.
- The caller MUST NOT perform the verification of section 9 with a domain taken from another source (for example a number registry). The reason is given in section 14 (man-in-the-middle attack).

**Trust.** For the domain received in the call, the handshake proves that it belongs to whoever answered the called number. This is the same trust that a spoken phone call deserves: if the number is right, the domain is right. Over A2A the caller may disclose the same data it would disclose verbally in the same call.

### 8.2 Endpoint resolution

1. The caller fetches the card from the A2A standard location: `https://<domain>/.well-known/agent-card.json`.
2. The connection MUST have a TLS certificate valid for the domain. If the certificate is invalid, the process is aborted.
3. On the card the callee advertises support for the protocol as an extension and gives the address of the handoff endpoint.

```json
"capabilities": {
  "extensions": [
    {
      "uri": "https://example.org/ext/phone-handoff/v0.3",
      "description": "Phone agent handshake (Agent Knock)",
      "required": false,
      "params": {
        "handoffUrl": "https://muster-zahn.ch/a2a/handoff",
        "phoneNumbers": ["+41311234567"]
      }
    }
  ]
}
```

- The extension's `uri` value here is a placeholder. Before publication it MUST be replaced with a final, self-controlled address.
- The `handoffUrl` address MUST be HTTPS and MUST be on the domain or one of its subdomains.
- In the `phoneNumbers` field the callee SHOULD list the numbers on which it supports the protocol. If the field is present and the called number is not in it, the caller does not send the S identifier and continues with speech.
- If the card is not reachable or does not contain the extension, the caller continues with speech.

## 9. Mutual verification on the data channel

Two HTTPS requests prove that the endpoint and the client are the same two parties that were in the call. The endpoint proves first, only then the caller.

### 9.1 Start: `POST {handoffUrl}/start`

```json
{ "version": "0.3", "session": "4821", "calledNumber": "+41311234567" }
```

Successful response (200):

```json
{ "proofA": "739104" }
```

- `calledNumber` is the called number in international format. It is useful when one endpoint serves several numbers.
- Verification can be started only once per session. A repeated request gets 409, an unknown or expired session gets 404.
- The caller compares the `proofA` value with its own A code. If it does not match, it MUST NOT send the B code; the process is aborted and the caller continues with speech.

### 9.2 Confirmation: `POST {handoffUrl}/confirm`

```json
{ "session": "4821", "proofB": "520466" }
```

Successful response (200):

```json
{ "accessToken": "...", "tokenType": "Bearer", "expiresIn": 900 }
```

- On a wrong B code the response is 403, and the session is invalidated immediately. There is no second attempt.
- The token is bound to this one session and is valid for at most 15 minutes.
- The endpoint MUST rate-limit requests per source address, so that the S identifier cannot be brute-forced.

## 10. Data exchange and ending the call

After successful confirmation, the caller sends standard A2A messages to the address given on the card, attaching the token in an `Authorization: Bearer` header.

- Facts (date, name, amount) SHOULD be sent as data parts, supplementary remarks as text parts.
- This specification does not fix the names of the data fields. The callee can state on its card what input it expects.
- Both parties MUST log the handshake and the A2A messages, so that their principal can read them afterwards.

**What happens to the call**

- The call MUST stay open until the end of the confirmation, so that speech can be resumed in case of an error.
- After the confirmation the caller may hang up. It SHOULD wait for the first A2A response, for at most 30 seconds.
- After the ACK the callee waits silently. If no start request arrives at its endpoint within 30 seconds, it continues with speech.
- If the matter requires a human decision, either party can return to speech in the still open call, or initiate a new call.

## 11. Implementation notes

**The frame handler is deterministic.** The random codes, the check digits and the frame verification MUST be handled by a deterministic component, not by a language model. An arithmetic error by the language model would produce an invalid frame or a wrong code.

There are two implementation paths:

1. **In the telephony layer** (for example Asterisk in front of the voice agent). The frame handler sends the ANNOUNCE when answering the call, listens for RFC 4733 events, replies itself, and the voice agent receives only the result of the handshake. This is the faster and more reliable path, and it also keeps the listening window (section 4) precisely.
2. **On the voice agent platform.** The platform passes incoming signals to the agent; the agent has the frame verified and the reply fetched via a tool (webhook), and then sends it with the platform's keypad tone tool. Here the response time of the language model must be taken into account (section 6). On the caller side this means that the HELLO in response to the ANNOUNCE may be delayed; this is why the callee must also accept the HELLO during the greeting.

**On the callee side the two paths can be combined:** the ANNOUNCE is sent by the telephony layer (a step run when the call is answered), the rest is handled by the voice agent.

**ElevenLabs-specific notes** (based on documentation, 2026-11-14; not tested):

- Sending: the "Play keypad touch tone" system tool sends an arbitrary `0-9 * #` sequence. On a SIP trunk the "Use out-of-band DTMF (RFC 4733)" option MUST be switched on; by default it sends in-band.
- Receiving: with the "DTMF input" setting, incoming signals go into a buffer, and the sequence reaches the agent as one user turn. `#` terminates the sequence and is not included, which fits the end of the frame. The buffer holds at most 50 signals. It accepts only signals arriving out of band, not in-band ones.
- Receiving: an incoming DTMF sequence during the greeting was delivered as DTMF input and interrupted the agent's speech (section 13, real-line test 2).
- The ElevenLabs first message starts immediately when the call is answered. The ANNOUNCE and the listening window SHOULD therefore be implemented in the telephony layer, before the call reaches the agent.

## 12. Error handling and timeouts

Every error leads to the same place: the two parties continue the call with speech, as if the handshake had never happened.

| Situation | Action |
|---|---|
| No ANNOUNCE arrives | The caller speaks and does not send HELLO. |
| No `*` arrives within 0.5 seconds after the ANNOUNCE | The callee greets. It still accepts the HELLO for 10 seconds from the end of the ANNOUNCE. |
| No OFFER starts within 6 seconds after the HELLO | The caller continues with speech. No retry. |
| Wrong check digits, wrong length or reserved code | The receiver sends NAK, the sender repeats the frame (for the OFFER group, the whole group). At most 2 repetitions, then ABORT. |
| Missing DOMAIN frame (more expected according to L) | The caller sends NAK 2 seconds after the last received frame. |
| More than 1 second elapses between two signals | The receiver discards the incomplete frame and sends NAK. |
| No ACK or NAK arrives within 6 seconds after the OFFER group | The callee repeats the group once, then continues with speech. |
| Unknown version or frame type | ABORT. |
| The domain received in the call differs from the known domain | ABORT, continue with speech (8.1). |
| The card is not reachable, or the extension is not in it | The caller continues with speech. |
| The called number is not in the card's `phoneNumbers` list | The caller continues with speech. |
| `proofA` does not match | The caller aborts the connection, does not send the B code, continues with speech. |
| The confirmation returns 403 | The session is invalid, the caller continues with speech. |
| The codes expire after 120 seconds | The endpoint returns 404, the caller continues with speech. |
| The handshake does not reach the ACK within 60 seconds from the HELLO | Either party sends ABORT. |

After a failed handshake, a new one MUST NOT be started in the same call.

When returning to speech, the caller SHOULD signal the switch with a short sentence, for example: "Sorry, I will continue by voice."

## 13. Measurement results (2026-11-13/14)

**Simulation** (local machine, frames sent in-band through codec and noise, own decoder, 10 trials per case):

| Codec | 5 signals/s | 7 signals/s |
|---|---|---|
| G.711 (landline, SIP) | 10/10 every frame | 10/10 every frame |
| G.726, Opus 12 kbit/s | 10/10 every frame | 10/10 every frame |
| GSM (old mobile) | short frame 9-10/10, long OFFER 7-9/10 | long OFFER 3-7/10 |
| Opus 6 kbit/s (weak mobile network) | with noise 0-1/10 | 0-5/10 |

**Real line:** mobile phone → Swiss mobile network → Swiss SIP provider → Asterisk.

| Transmission | Result |
|---|---|
| In-band (loudspeaker held to the mobile's microphone, 12 frames) | 0/12. The 1000 Hz start tone got through, but faded to about one sixth within about 1 second; only single-frequency fragments of the DTMF remained. Probable cause: noise suppression in the phone or the network. |
| Out of band (keypad, 7 signals: `1 2 3 4 5 * #`) | 7/7, in order. The network adjusted every signal to 70 ms. Asterisk pads a signal shorter than 80 ms rather than discarding it. |

**Conclusion:** frames sent in-band cannot be relied upon; out of band, transmission is reliable. The RFC 4733 obligation in section 5 follows from this.

### Real-line test 2 (2026-11-14)

- **Caller to callee** (`*10#`, a keypad test sequence rather than a valid frame, typed on the mobile keypad while the callee agent was greeting): delivered end to end out of band. Mobile → SIP provider as RFC 4733 (payload type 97) → Asterisk → ElevenLabs agent as RFC 4733 (payload type 101). The ElevenLabs agent received it as DTMF input and the input interrupted its greeting. Digits arrived on the line at about 57-61 ms each; Asterisk extended them to its 80 ms minimum.
- **Callee to caller** (ANNOUNCE `*140360#` sent by Asterisk at pickup): Asterisk sent the RFC 4733 events (about 80 packets, 7 digits, 100 ms each) towards the SIP provider, but the human caller heard no tone on the mobile phone. The events are lost or not rendered as audio on the provider/mobile side. For a human caller this is the desired behaviour.
- **Still not measured:** whether ANNOUNCE reaches a calling AI agent that is itself on SIP (agent-to-agent call through a different provider); full handshake timing between two real agents; ElevenLabs keypad-tone tool behaviour on the sending side.

## 14. Security considerations

The protocol proves exactly one thing: at both ends of the data channel are the same two parties that were in the call. It does not prove that the callee is who the caller believes it to be. Any further protection is the task of the application.

**What the protocol prevents**

- Foreign endpoint: whoever was not in the call does not know the A code, and is therefore exposed in step 9.1 before learning anything.
- Foreign client: whoever was not in the call does not know the B code, and therefore receives no token.
- Incorrectly transmitted frame: the check digits and the length check filter it out.
- Code guessing: the codes are single-use, live for 120 seconds, and there is a single attempt for the B code.

**Man-in-the-middle attack, and why the domain must come from the call.** If the caller took the domain not from the call but from a false source (for example a lying number registry), the attacker's endpoint could relay the requests to the real endpoint: it obtains the A code from it, returns it to the caller, takes the B code, and from then on sits between the two parties. Binding the 6-digit code to the endpoint's domain (for example with HMAC) is not enough, because the attacker can recover the code from the bound value within seconds. This is why section 8.1 requires that verification may only take place with the domain received in the call: it is sent by the real callee, and whoever cannot modify the call cannot replace it.

**What it does not prevent**

- **False phone number.** If the caller dials a number taken from a false source (for example a forged company profile), the fraudster answers and sends their own domain. It passes every check, just as in a spoken call the caller would be talking to the fraudster. If the caller also knows the domain from the same source, it notices the discrepancy (8.1).
- **Hijacked phone number:** in case of a SIM swap or unauthorised call forwarding, the attacker answers the phone. This applies equally to traditional telephony.
- **Passive eavesdropping.** The S, A and B codes travel in the clear in the call; with RFC 4733, in the event packets, which every provider along the call path can see. Whoever hears the call can race the caller on the `/confirm` request. The damage is a spoiled handshake or, if the attacker is faster, a token valid for 15 minutes for this one session.
- **Attacker inserted into the call:** whoever can modify the call can also replace the codes and the domain.
- **False ANNOUNCE:** anyone can send an ANNOUNCE. This only achieves that the caller sends HELLO; the further steps of the handshake protect just the same.
- **Identity of the caller:** the callee knows only that the client was in the call. Not on whose behalf it acts, nor what it is authorised to do.
- **Hijacked session:** whoever guesses the S identifier can start the verification before the real caller. They receive no token, but the handshake fails. Rate limiting makes this rarer, but is weak against attempts from many source addresses.

**Tasks of the application**

- Narrow mandate: per task the agent discloses only the necessary data, with financial and commitment limits.
- The other side's message is data, not instruction: the agent accepts fixed fields and does not execute the other agent's text as commands.
- Separated negotiating part: the component that talks to the other agent should not have access to the principal's complete data.
- Human approval: before an irreversible or costly step, the agent checks back with its principal.
- **AI disclosure:** if the agent communicates by speech (the handshake did not take place or failed), it MUST state at the beginning of the conversation that it is an AI. This applies to both caller and callee. The ANNOUNCE does not replace this, because a human does not understand it.

## 15. Open questions

- Acceptability of the ANNOUNCE for human callers on paths where it becomes audible (for example landlines behind a gateway that renders RFC 4733 as audio): how disturbing is the tone after pickup? It must be tried with real callers before it is switched on on a live line.
- Interrupting the greeting: with a 0.5-second listening window the HELLO of a caller running on a language model will usually arrive during the greeting. Can voice-agent platforms stop their own speech reliably on an incoming DTMF event?
- Measurement of the complete handshake between two real agents over SIP, including the language model's response time.
- ElevenLabs, sending side: does the keypad tone tool really use RFC 4733 with the option switched on, and at what rate does it send the signals? (Receiving side answered: incoming DTMF interrupted the greeting, see section 13, real-line test 2.)
- Reverse direction: what should happen if only the caller has an endpoint and the callee does not?
- Stronger verification: if verification ever had to be possible with a domain taken from another source, then instead of codes in the clear a password-authenticated key exchange (PAKE, for example CPace) bound to the endpoint's domain would be needed. This would also eliminate the man-in-the-middle attack and the hijacked session. Is it worth the added complexity?
- Submission to the A2A community as a telephony extension.
- Legal questions: the mandatory wording of the AI disclosure and the data protection conditions for logging, per country.

## Appendix: worked example

An assistant agent books an appointment at the Muster dental practice. The caller knows only the phone number (+41 31 123 45 67), which its principal gave it.

1. **ANNOUNCE.** On answering the call, the practice's telephony layer sends: `*140360#` (14 = ANNOUNCE, 03 = version, 60 = check digits). Then it waits 0.5 seconds.

2. **HELLO** (A = 739104), within the window or during the greeting

```
*100373910455#
10      type: HELLO
03      version
739104  A code
55      check digits
```

3. **OFFER** (S = 4821, B = 520466, domain `fogaszat-muster.ch`, 18 characters)

```
*110348215204661806150701192601204013211920051841#
11      type: OFFER
03      version
4821    session identifier
520466  B code
18      domain length
061507011926012040132119200518   fogaszat-muster (first 15 characters)
41      check digits
```

4. **DOMAIN 1**, after a pause of at least 300 ms

```
*13141030866#
13      type: DOMAIN
1       sequence number
410308  .ch
66      check digits
```

5. **ACK**

```
*1262#
```

6. **Fetching the card** from the domain received in the call: `GET https://fogaszat-muster.ch/.well-known/agent-card.json`. From it: `handoffUrl = https://fogaszat-muster.ch/a2a/handoff`, and the `phoneNumbers` list contains the number +41311234567.

7. **Start**

```
POST https://fogaszat-muster.ch/a2a/handoff/start
{ "version": "0.3", "session": "4821", "calledNumber": "+41311234567" }

200 OK
{ "proofA": "739104" }
```

The caller checks: 739104 matches its own A code.

8. **Confirmation**

```
POST https://fogaszat-muster.ch/a2a/handoff/confirm
{ "session": "4821", "proofB": "520466" }

200 OK
{ "accessToken": "eyJ...", "tokenType": "Bearer", "expiresIn": 900 }
```

9. **Business over A2A.** Content of the messages' data parts, in outline (not literal A2A syntax):

```
caller → { "request": "appointment", "period": "2026-11-16/2026-11-20", "timeOfDay": "afternoon" }
callee → { "available": ["2026-11-17T14:00", "2026-11-19T16:30"] }
caller → { "choice": "2026-11-17T14:00", "name": "X. Y.", "phone": "+41 79 000 00 00" }
callee → { "status": "booked", "appointment": "2026-11-17T14:00" }
```

10. **Closing.** The caller hangs up, enters the appointment in its principal's calendar, and saves the log.

**If a human calls:** the practice sends the ANNOUNCE; depending on the network the caller hears a short tone or nothing, and says something ("Hallo?"). The callee agent greets immediately, states that it is an AI assistant, and the call continues with speech.
